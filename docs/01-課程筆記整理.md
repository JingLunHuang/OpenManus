# OpenManus 開發實戰 · 課程筆記整理
---

## 1. OpenManus 是什麼

- MetaGPT 團隊開源的通用智慧代理框架，目標是零成本復刻閉源 Manus"手腦並用"的能力：把自然語言需求變成可執行的工作流，內建瀏覽器自動化、Python 執行、檔案處理、視覺化等工具，工具可插拔。
- 專案地址：<https://github.com/FoundationAgents/OpenManus>；社群 Web UI：<https://github.com/aliasmaya/openmanus-ui>。
- 課堂上的一個好用的心智模型：

  | 形態 | 組成 | 擅長 |
  |---|---|---|
  | 千問 / 豆包等對話產品 | LLM + web_search | 問答、檢索 |
  | OpenManus | LLM + web_search + **browser_use_tool** | 操作**沒有 API 的網站** |
  | 加上經驗庫 | Agent = LLM + Tool + RAG | RAG 影響初始 prompt：System Prompt + Tool Prompt + RAG chunks |

### 1.1 六層架構

| 層 | 內容 |
|---|---|
| 使用者互動層 | CLI、Web API、視覺化介面 |
| 應用入口層 | `main.py`（單智慧代理）、`run_flow.py`（多智慧代理協作）、`run_mcp.py`（遠端工具） |
| 智慧代理層 | `BaseAgent → ReActAgent → ToolCallAgent → Manus` 四級繼承，逐級疊加"推理—行動—工具呼叫" |
| 工具層 | 統一 `BaseTool` 介面：瀏覽器、搜尋、程式碼執行、檔案編輯；可經 MCP 擴充 |
| 流程控制層 | `PlanningFlow` 把複雜任務拆成線性/DAG 步驟，按角色分工 |
| 基礎設施層 | Docker 部署、多模型適配（DeepSeek / Claude / Qwen 等）、沙箱 |

典型場景：資料採集與視覺化（自動寫爬蟲 → 清洗 → 出報告）、電商運營（多平臺文案、競品價格抓取）。

## 2. 主流程程式碼走讀

```
python main.py
  └─ agent = await Manus.create()          # 建立實例、連線 MCP
  └─ await agent.run(prompt)               # BaseAgent.run：主迴圈
        while current_step < max_steps(20) and state != FINISHED:
            step()                          # ReActAgent.step
              ├─ think()                    # 決策：選哪些工具
              └─ act()                      # 執行：跑工具、寫回記憶
```

- **think()**（`Manus.think` → `ToolCallAgent.think`）
  1. 若瀏覽器工具可用，用 `BrowserContextHelper.format_next_step_prompt()` 把 URL、標題、可互動元素列表拼進 next_step_prompt；
  2. `llm.ask_tool(messages, system_msgs, tools=available_tools.to_params(), tool_choice=AUTO)`；
  3. 記錄思考內容與工具呼叫，寫入記憶；返回"是否有工具要執行"。
- **act()**（`ToolCallAgent.act` / `execute_tool`）：逐個執行工具呼叫 → 結果（含截圖 base64）作為 `tool` 訊息寫回記憶。
- **記憶**：`Memory.messages` 按 user / assistant(含 tool_calls) / tool / system 四種角色不斷追加，下一輪 think 基於全部歷史。
- **卡死檢測**：連續出現相同 assistant 內容 ≥2 次時，在提示詞前加一句"請換策略"。

| 函式 | 位置 | 作用 |
|---|---|---|
| `run()` | agent/base.py | 主迴圈 |
| `step()` | agent/react.py | think + act |
| `think()` / `act()` / `execute_tool()` | agent/toolcall.py | 決策 / 執行 / 單個工具呼叫 |
| `get_browser_state()` / `format_next_step_prompt()` | agent/browser.py | 讀取瀏覽器狀態、格式化提示詞 |
| `execute()` / `get_current_state()` / `_ensure_browser_initialized()` | tool/browser_use_tool.py | 瀏覽器動作、頁面狀態、懶載入瀏覽器 |

## 3. 瀏覽器工具 BrowserUseTool

- 基於 browser-use（底層 Playwright），動作包括 `go_to_url / click_element / input_text / scroll_* / send_keys / extract_content / 標籤頁管理 / wait` 等。
- **元素編號機制**：DomService 遍歷 DOM，把識別為可互動的元素（button、input、a……）編號，並在頁面上注入編號標籤，生成
  `[index]<type>text</type>` 列表；模型據此選擇 `click_element(index=N)`。
- **設計取捨**：用文字描述代替截圖，省錢、快；代價是——**不在列表裡的元素，模型永遠看不到**。這正是攜程日曆失敗的根源（見 6.3）。

## 4. Prompt 體系與本地化改造

- **Manus 系統提示**：全能助手身份；工作目錄；即時資訊（機票、天氣、股價、新聞）必須用瀏覽器獲取、不準編造；用中文回覆。
- **Manus next_step 提示**：主動選擇工具、複雜任務分解、每步解釋結果；想結束時呼叫 `terminate`。
- **Browser 系統提示**：規定輸入格式（元素列表）、嚴格 JSON 響應（evaluation_previous_goal / memory / next_goal + action 列表）、完成時用 done、在 memory 裡計數進度等。
- 課程裡對原專案做了兩處改造：①漢化（提示詞、日誌）；②加 Web UI（把 openmanus-ui 的 assets / static / templates / app.py 拷進專案，`python app.py`）。
- 模型配置在 `config/config.toml`：文字 `qwen-max`、視覺 `qwen-vl-plus`；也可以用同時支援文字與視覺的 `qwen3.x-plus`。

## 5. Daytona 雲沙箱

- 作用：把 AI 生成的程式碼放進隔離容器執行，只把結果帶回，宿主機不受影響。
- 用法：`pip install daytona` → 在 app.daytona.io 申請 API Key → `Daytona(DaytonaConfig(api_key=...)).create()` → `sandbox.process.code_run(code)`。
- OpenManus 中的整合：`app/daytona/`（沙箱建立與工具基類）+ `app/tool/sandbox/`（沙箱瀏覽器 / 檔案 / Shell / 視覺工具）+ `SandboxManus` 智慧代理。
- SandboxManus 初始化：建立沙箱 → 啟動 supervisord（行程守護，掛了就重啟）並等待瀏覽器服務就緒 → 生成 VNC 與網站連結 → 掛載沙箱工具 → 連線 MCP；使用者可透過 VNC 即時看沙箱裡的瀏覽器。

  | | BrowserUseTool（Manus） | SandboxBrowserTool（SandboxManus） |
  |---|---|---|
  | 執行位置 | 本地電腦 | Daytona 雲端 |
  | 檢視方式 | 直接看到瀏覽器視窗 | VNC 連結 |
  | 資源佔用 | 本地 | 雲端 |

- 注意：Daytona 的 tier1 / tier2 賬戶沙箱**不能上網**，需要 tier3 以上。

## 6. 三個實戰案例

### 6.1 網站 SEO 審查
任務：對 `http://class.wucai.com` 做 SEO 審查並寫入 `.md`。
執行軌跡：`go_to_url` → 連續多次 `extract_content`（頁面標題、描述、關鍵詞、meta、H1、H2……），第 8 步才開始規劃"內容質量、URL 結構、圖片 alt、內外鏈、移動端、載入速度、結構化資料"。
**問題**：每項檢查佔一步，20 步的上限很快被耗盡。

### 6.2 競品分析報告
任務：2026 年中國新能源汽車出海歐洲的競品分析，重點比亞迪、小鵬。
- 搜尋引擎：`WebSearch` 支援 google / baidu / duckduckgo / bing，按配置順序回退。
- **問題**：OpenManus 會把"收集資訊"再拆成"搜 A 的功能、A 的定價、A 的評價……"，一個環節就佔 3~6 步；搜到的新聞常常過時，報告失真（課堂追問：要讓結果變好，只換模型夠不夠？——不夠，檢索策略與時效約束同樣重要）。

### 6.3 攜程機票查詢（全課重點）
任務：查詢某日從上海到北京的機票。

| 輪次 | 行為 | 結果 |
|---|---|---|
| 修復前 | 反覆點日曆、瞎猜元素編號 | 20 步耗盡，失敗 |
| 僅加"直連結果頁 URL" | 直接跳深鏈，但日期是 `2023-06-26` | 年份錯 + 被 whaleguard 反爬攔截（頁面空白、0 個元素、截圖僅 10KB） |
| 完整修復 | 先造訪首頁建立會話 → 再跳 `depdate=2026-06-26` | 進入結果頁，提取到 8 個真實航班 |

- **根因（排查結論）**：模型從頭到尾沒看截圖，只靠文字元素列表猜編號；而攜程日曆恰恰是"看著格子點"的視覺化控制元件。開了除錯開關後對比第 06 號快照：**截圖裡有日曆，元素列表裡沒有日曆，HTML 裡也搜不到"26"**。
- 除錯手段：在 `get_current_state` 里加 `_BROWSER_DEBUG`，每次把 HTML、元素列表、截圖存進 `browser_debug/`。
- 其他坑：模型不知道今天是哪一年（把"6月26日"解析成 2023 年）；把步數改成 25 時，`browser.py` 裡的 `max_steps` 也要一起改；去哪兒會彈登入框，飛豬會跳轉淘寶。

## 7. 兩種增強策略

### 方法 1：RAG 策略（OpenManus-rag）
1. **元素分類器** `element_classifier.py`：把元素分為 14 類（CALENDAR、DATE、INPUT、BUTTON、LINK、SELECT、TAB……），每個元素 0~100 置信度；1~31 的數字自動標成日曆格。
2. **知識庫**：啟動時讀取 `knowledge/*.txt` 注入系統提示；首個場景是"機票查詢用 URL 參數直達，繞開日曆"。
3. **系統時間注入**：提示詞裡寫明當前日期時間與星期。
4. **完成策略**：優先從元素列表取資訊、少調 extract_content；查詢類任務拿到結果立即 terminate，不反覆確認。

### 方法 2：GUI 策略（OpenManus-gui）
1. **gui-plus 模型**：輸入截圖 + 指令，輸出 `{"thought", "action", "parameters"}`，動作為 CLICK / TYPE / SCROLL / KEY_PRESS / FINISH / FAIL，座標為畫素。
2. **簡化介面**：把"按編號操作"改成 `click(element_description)` / `type(element_description, text)`，內部三層定位：Playwright 文字定位 → JavaScript 查詢 → GUI-Plus 視覺兜底。
3. **日期處理**：提示詞寫明當前年份；`go_to_url` 裡自動把攜程 URL 中過期的日期改到今年/明年。
4. **除錯**：每次操作儲存 HTML 與元素資訊；視覺操作儲存截圖並畫出點選位置。
5. 實戰中遇到的問題：模型返回的座標 JSON 不規範（`{"x": 139, 675}`、`{"x": [139, 675]}`）；輸入框打字不生效（出發城市仍是"新加坡"）；提示詞裡不應寫具體城市、數值示例，要追求泛化。

**課程結論**：RAG 策略相對確定，但要一個場景一個場景地補；gui-plus 更通用，但結果更不確定。

## 8. 課堂問答要點

- **求職與作品集**：先把專案寫進簡歷；專案要打分排序；GitHub 的 README 至少寫清"XXX 瀏覽器 Agent，能幫使用者完成 XXX"、架構圖、CASE1 競品分析 / CASE2 攜程機票查詢。
- **意圖識別**：類別不要太多；用 few-shot 測試準確率；兜底寫得太多容易變成屎山；面試常問"兜底失敗了怎麼辦、為什麼這麼設計"。
- **編排能力**從哪來：本質靠 LLM 本身的規劃能力。
- **RAG 知識更新**：raw data → chunks → embedding → 向量資料庫，資料更新就是重跑這條鏈。
- **成本**：token 很貴（"2 天用了 500 塊"），任務時間長 = 費 token，免費額度只夠跑三四輪。
- **模型選擇**：文字 qwen-max；視覺 qwen-vl；文字+視覺 qwen3.x-plus；DeepSeek 價效比高適合大量呼叫；GLM 較貴。
- **MCP 還是瀏覽器**：有 MCP 就用 MCP（更準，出錯也有明確責任方），但可能收費；瀏覽器工具主要解決"沒有 API 的網站"。
- **穩定性**：Agent 的穩定性很重要，取決於工具質量 + 模型能力。
- 其他：截圖目前是全屏，可以限定區域；登入彈窗會讓後續操作全部失敗；效能指標關注 TTFT（首 token 延遲）；本地部署可用 docker compose。

## 9. 從課程到「靈犀」：問題 → 新機制

| 課程中的問題 | 靈犀的做法 | 程式碼位置 |
|---|---|---|
| 日曆格子不在元素列表裡 | 自研頁面快照：cursor:pointer 啟發式 + 日期格語義 + 月份上下文 | `lingxi/senses/dom_snapshot.js` |
| 視覺座標不可靠、格式亂 | 視覺結果必須經 `elementFromPoint` 反查 DOM 交叉驗證；統一解析多種座標格式 | `senses/grounding.py`、`senses/vision.py` |
| 輸入了"上海"，實際還是"新加坡" | 每個動作"定位 → 執行 → 驗證"：回讀輸入值、列出聯想候選、未觀察到變化就標"未驗證" | `skills/web.py` |
| 年份被當成 2023 | 時間錨定：任務進入模型前就把日期解析成絕對日期寫回任務 | `knowledge/temporal.py` |
| 深鏈被 whaleguard 攔截 | 手冊宣告預熱首頁，瀏覽器層在首次造訪站點時強制先開首頁 | `knowledge/playbook.py`、`senses/browser.py` |
| 知識庫是一段 txt，模型自己拼 URL | 宣告式 TOML 手冊：匹配 → 填槽 → 代碼表 → 編譯出直達 URL | `playbooks/*.toml` |
| 20 步硬上限，改大又浪費 | 進展感知預算：有可驗證進展就續航，原地打轉扣減，最後一步強制收尾 | `kernel/budget.py`、`kernel/hooks.py` |
| token 太貴 | 頁面狀態只在本步簡報出現；舊觀察摺疊成一行；按任務模式裁剪工具集 | `kernel/memory.py`、`kernel/profiles.py` |
| 靠手動加日誌排障 | 黑匣子：所有事件寫入 events.jsonl，控制台 / Web UI / 復盤報告都是它的訂閱者 | `lingxi/journal/` |
| 意圖識別與兜底 | 四類模式，規則優先、手冊指定、LLM 可選兜底，識別不出落到 general | `kernel/intent.py` |
| 登入彈窗擋住操作 | 快照檢測遮擋圖層並給出可能的關閉按鈕編號 | `dom_snapshot.js`（overlay） |
| 競品報告引用過時新聞、答覆混入模型自己的數字 | 反覆查證：發現板標示多源印證 / 矛盾；finish 前逐條核對證據，無據退回補查 | `kernel/verify.py`、`kernel/boards.py` |
| 課程是簡體、網站是簡體，但使用者用繁體 | 繁簡通吃：繁體指令可定位簡體網頁，簡體任務一樣能錨定日期、命中手冊 | `lingxi/hanzi.py` |

詳見 [02-靈犀架構設計.md](02-靈犀架構設計.md)。

## 10. 安全提醒

舊版 `OpenManus-*/config/config.toml` 中有一個**明文的 Daytona API Key**（`dtn_` 開頭）。舊程式碼已移出專案目錄；如果這份配置曾經被上傳、分享或提交到任何倉庫，請到 Daytona 控制台作廢並重新生成。靈犀只從環境變數或被 `.gitignore` 忽略的 `config/lingxi.toml` 讀取金鑰。
